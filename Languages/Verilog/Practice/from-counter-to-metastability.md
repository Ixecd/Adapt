# 从计数器到亚稳态：一下午的时序推理链（2026-09-03）

> 从写第一个 counter，到理解"物理只看稳态"——这条推理链是手动推导出来的，比看十遍书都值。

## 0. 起点：counter 波形分析

写了 4bit 累加计数器 + testbench，Surfer 看波形：

- `rst_n` 在 20000ps(20ns) 拉高 → 复位释放，之后才开始计数
- `count` 每个 clk 上升沿 +1：0→1→2→...→9→a→f→0（a/f 是十六进制显示）
- 4bit 无符号 → 最大 f(15)，溢出回 0（进位丢弃）
- 时钟周期 10000ps(10ns)

**testbench 本质**：手动模拟外部世界（生成时钟、给复位、喂信号），看被测模块怎么反应。

## 1. 三段式状态机的三段到底怎么执行

seqdet（1011 序列检测器）三段式，核心疑问：段1/2/3 是同时执行还是顺序？

**真相**：
```
段2（always @*，次态）= 组合逻辑：信号一变就重算，无时无刻在跑
段3（always @*，输出）= 组合逻辑：同上
段1（always @(posedge clk)，跳转）= 时序：只在时钟沿执行
→ 不是"三个在沿同时执行"
→ 是"组合无时无刻算（段2/3）+ 时序只在沿采纳（段1）"
→ 段2/3 像"电路直连"（信号流过就出结果），段1 像"照相机快门"（沿才咔嚓）
```

## 2. state <= next_state：沿前采样，但采的是 next_state 不是 state

**最大误区**：以为 `state <= next_state` 采的是"沿前的 state"。

**真相**：`A <= B` 沿采的是 **B 的当前值**（组合算好的 next_state），沿后 A 变成它。
```
next_state 是组合：state=S101 + din=1 → 恒等于 S1011（跟沿无关）
沿一到，state 采纳 next_state（S1011）→ 一拍进状态4
不存在"state 卡在 S101"——那是把"沿前 state"和"沿前 next_state"搞混
```

**为什么 detected 能持续 10ns**（S1011 里 next_state=IDLE，但 detected 1 持续一拍）：
```
state 只在沿变。S1011 状态下 next_state=IDLE 只是"预定下个沿去哪"
state 在 S1011 停整个时钟周期（等下一个沿才走）
detected 是组合（跟随当前 state）→ state 停 S1011 多久，detected 就 1 多久
```

## 3. 组合 always 是"事件驱动"不是 while(1)

`always @*` = "块里用到的信号一变，执行一次，算完挂起等下一个变化"
- 不是无条件忙等（while(1)）
- 是"输入变化触发的组合计算循环"

## 4. 仿真器的时间片调度（信号先于时钟？）

疑问：同一时刻 din 变化 + clk 沿，谁先？

**仿真器分层调度顺序**（串行模拟并行物理）：
```
1. 活跃事件：信号变化/阻塞赋值（din=1）
2. 组合逻辑（@*）→ 被唤醒重算（段2 → next_state=S1）
3. 时序采样（clk 沿）→ 段1 采样（采到最新的 next_state）
4. 非阻塞赋值更新
→ 信号变化的逻辑处理普遍先于时钟采样
→ 模拟真实硬件"组合先稳定、时序后采样"
```

**但**：仿真器是串行排队"假装同时"，物理是真同时（加电全开）。两者结果一致的前提 = "组合在沿前稳定"。

## 5. 撞沿：仿真 vs 物理的天壤之别

testbench 里 din 在 25ns 变 1 正好撞 clk 上升沿：

```
仿真器：按调度顺序给"确定结果"（din 先 → 组合先算 → state 采到 S1）
        → 不是 X（仿真器理想化，默认不模拟亚稳态）
物理真硬件：din 撞沿 → 建立/保持时间违例 → 亚稳态 → 可能 X
        → 结果不确定（可能错）
→ 撞沿是 testbench 缺陷：仿真给"确定但不真实"的结果，掩盖了物理亚稳态
→ 所以 testbench 要错开沿（信号沿后 1-2ns 变），模拟真实器件的输出延迟
```

## 6. 物理上怎么解决：时钟 = 统一时间基准（错开瞬态）

```
同步设计（同源时钟）：不用刻意岔开
  发方沿后输出（tco 延迟）→ 收方下个沿采
  → 时钟周期天然提供"一拍"间隔 → 信号在沿间稳定 → 安全
异步输入（跨时钟域/外部随机）：时钟管不住
  → 可能撞沿 → 亚稳态
  → 打两拍：第一拍采到亚稳态，第二拍给它时间稳定（两拍缓冲）
→ 时钟的终极意义 = 给所有逻辑一个"采样时刻"，让瞬态有地方被丢弃
```

## 7. 终极哲学：物理只看稳态，不看瞬态

```
组合逻辑：给足时间（传播延迟）→ 输出稳定 → 才算数
触发器：只在沿采样 → 采"稳定后的值"
建立/保持时间：框定"稳态窗口"（沿前够稳、沿后别变）
瞬态（毛刺/中间值）：只要在采样前结束，无所谓
→ 数字世界用"时间窗口"隔离瞬态，只保留干净的 0/1 稳态
→ "物理不在乎改变的那一瞬间，只在乎稳态" = 数字设计公理
→ 这也是数字电路"抗噪"的原因（主动丢弃采样窗口外的瞬态）
```

## 8. 仿真 vs 物理的本质差距（一句话）

```
仿真 = 用串行计算模拟并行物理（排队模拟同时）
物理 = 真同时（加电全开），靠"传播延迟 + 建立时间"保证正确
→ 仿真器是"模拟器"，不是硬件本身
→ 别被仿真的"确定结果"骗了——撞沿处物理可能是亚稳态
```

## 10. seqdet.v 本身没问题，问题在 testbench 撞沿

```
seqdet.v（模块）：状态机逻辑正确（IDLE→S1→S10→S101→S1011，Moore 输出，default 防御）
  → 模块本身没 bug，可综合

seqdet_tb.v（testbench）：din 用 #10 间隔变，时钟也 10ns 周期 → din 撞上时钟沿
  → 撞沿 = testbench 缺陷（din 该错开沿 1-2ns 变，模拟真实器件输出延迟）
  → 不是 seqdet 模块的错，是激励没对齐协议

结论：要改的是 testbench，不是模块
```

## 11. 物理世界真撞沿有影响吗？

```
物理上异步输入（按键/传感器/跨板信号）确实会撞沿 → 亚稳态 → 概率性错
但有影响吗？→ 有，但被设计控制到"几乎没影响"：
  异步输入撞沿 → 打两拍（sync2）→ 亚稳态概率降到可忽略
  同步输入 → 不该撞（发方沿后输出，天然错开一拍）
→ 撞沿影响 = 概率 × 信号关键性
  非关键：偶尔错能恢复 → 影响小
  关键（安全）：严格打两拍 → 影响趋零
→ 物理撞沿真实存在，设计（打两拍+余量）让"可能错"变"几乎不错"
```

## 12. 为什么 seqdet 里没有打两拍——模块化分层

```
seqdet 假设输入"已同步好"（干净），它不负责处理异步
打两拍是"输入接口层"的事：
  真实系统：异步din → [sync2 打两拍] → 同步din → seqdet
→ 分层：
  sync2（同步模块，处理异步输入）
  seqdet（逻辑模块，处理干净输入）
→ seqdet 里没有打两拍 = 正确（它不该管，职责分离）
```

## 13. 段2 为什么用 =（阻塞），不用 <=（非阻塞）

```
段2 是组合逻辑（@*）→ 必须用 =（时序逻辑才用 <=）
关键：段2 的写法是"先默认 next_state=state，再 case 覆盖成目标态"
  → 这种"先默认后覆盖"必须用 =（顺序执行才能覆盖）
  → 如果用 <=：非阻塞"预定不分先后"，默认和覆盖同时预定 → 覆盖失效
→ 铁律：组合(@*)=，时序(clk)<=
  段1 时序用 <=（同时更新），段2 组合用 =（顺序覆盖）
```

## 14. FPGA 不按顺序跑，怎么"覆盖"？——综合成 MUX

```
段2 的"顺序执行"不是 FPGA 真按顺序跑，是代码语义：
  next_state = state; 然后 case 覆盖成 S1
→ 综合器翻译成 MUX/选择逻辑：
  next_state = 条件 ? S1 : state（后面的赋值优先级高）
→ 硬件是"并行选择/覆盖"，不是"顺序执行"
→ 不需要"谁保证顺序"，也不需要"外部同步模块"
  （同步模块是给跨时钟域的，不是给组合逻辑赋值顺序的）
→ 组合逻辑的"覆盖顺序" = 综合器翻译成 MUX，天然成立
```

## 15. a=b; a=c 综合成什么？

```
仿真器：顺序执行 → a=b 再 a=c → 最终 a=c（覆盖）
真实 FPGA：综合器做"死代码消除"
  → a=b 马上被 a=c 覆盖（没人读 b）→ 去掉 → 只留 a=c
→ 结果等价 a=c，但过程是综合器的化简
→ 和编译器优化一样（x=1; x=2 → 优化成 x=2）
→ 区别：硬件"更强制"（a 只能一个驱动源，前面的必然丢）
```

## 16. 综合器的本质：结果导向，消中间逻辑

```
综合器不看 case 每条代码块"怎么执行"（过程）
只看"每个 (state, din) 组合最终 next_state 是啥"（结果）
→ 汇总成一张映射表（真值表）
→ 优化成最简逻辑网络（MUX/与或）
→ 中间变量/被覆盖赋值/临时计算 → 全消（不影响最终输出的都优化掉）
→ 从"过程描述"到"结果映射" = 综合的本质
对比软件：
  软件（CPU）：按代码一步步执行（过程重要，中间步骤真跑）
  硬件（FPGA）：综合成"结果映射"（过程消掉，只要输入→输出）
→ 仿真看过程（包括中间），综合看结果 → 中间有副作用会分歧
→ RTL 准则：只写"影响最终结果"的逻辑，别依赖中间过程
```
