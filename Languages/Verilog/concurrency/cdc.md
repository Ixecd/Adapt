## concurrency/ 并行与跨时钟域（预留位）

这是软件人最容易忽略、但 FPGA 最容易翻车的部分。对应 Go 的 concurrency。

### always 块并行
多个 always 块物理并行，没有"顺序"概念（和 goroutine 本质区别：硬件真并行，软件靠调度）。

### begin-end 串行 vs fork-join 并行（都是仿真抽象）

```verilog
// begin-end 顺序块：一条条执行，上一条完成才下一条（模拟串行）
begin
    a = #10 1;   // 等10
    b = #10 2;   // 再等10 → 总20
end

// fork-join 并行块：所有同时启动，各自独立计时（模拟并行）
fork
    a = #10 1;   // 等10
    b = #10 2;   // 同时等10 → 总10
join
```

**关键**：两者**都是仿真器的抽象**，不是物理真并行：
```
begin-end：模拟"先后顺序"（串行）——上一条完成才下一条
fork-join：模拟"同时并行"——仿真器"同时启动所有语句 + 各自独立计时"，结果像并行
真硬件：加电全开，物理真同时（没有"启动顺序"这回事）
```

- fork-join 里语句仍被"按顺序启动"，只是各自延时独立计时 → 看起来同时完成
- 真正的"物理并行"只有加电全开那一种，仿真器的一切（begin/fork/=）都在用抽象模仿它
- fork-join 基本**不可综合**，只用于 testbench（让多个激励"看起来同时跑"）；可综合代码几乎只用 begin-end

### 并发 vs 并行：begin + <= 就是并行

**软件概念映射到硬件**：
```
并发（concurrency）：逻辑上同时，但可能交错执行（单核多线程轮流跑）
并行（parallelism）：物理上真同时（多核/硬件加电全开）
```

**Verilog 里四种组合的本质**：
```
begin + =  ：串行（一条条执行）
begin + <= ：并行（同一时刻点所有预定一起提交）← 这就是"并行"
fork  + =  ：并发（同时启动但各自阻塞，交错计时）
fork  + <= ：并行（同时启动 + 同时提交）
```

**关键：并行的根源在 `<=` 的语义，不在块的类型**：
```verilog
begin
    a <= 1;   // 预定
    b <= 2;   // 预定
end
// 同一时刻点，a 和 b 一起更新 → 真"同时生效" → 并行
```
- `<=` 的核心 = "同一时刻点所有预定一起提交"（真同时 = 并行），begin 只是顺序启动这些预定
- 而 fork + `=` 是"同时启动但各自阻塞"（交错计时），更接近"并发"

**一句话**：`<=` 天生是并行语义——放 begin 里也并行，放 fork 里也并行；fork + `=` 才是并发。**判断并发/并行看 `<=`（同时提交）还是 `=`（各自阻塞），不看 begin/fork**。

**实际用途（fork 没用，但这个区分有大用）**：
- fork 不可综合，只在 testbench 用，可综合 DUT 不写 fork——fork 本身用不上
- 但"`<=` 同时提交 / `=` 顺序交错"正是理解"**时序用 `<=`、组合用 `=`**"的根：
  ```
  a <= b; c <= a;  → c 拿 a 旧值（同时提交，都取"提交前"的值）
  a = b;  c = a;   → c 拿 a 新值（顺序交错，先更新 a 再给 c）
  ```
- 死记"时序用<="不如理解"<="的并行提交语义——避坑的底层原因在这

### 状态机 = 带时钟的 DP（软件 vs 硬件的终极分界）

**三大方程 vs DP 递推同构**：
```
状态机三大方程：
  状态转移方程：next_state = f(current_state, inputs)   ← 状态怎么变
  状态方程：    current_state = next_state（沿锁存）    ← 状态怎么存
  输出方程：    output = g(current_state, inputs)       ← 状态怎么输出

DP 递推：
  状态转移：dp[i] = f(dp[i-1], inputs)   ← 状态怎么算
  状态存储：dp 数组                        ← 状态怎么存
  结果：dp[i] 读答案                       ← 状态怎么取
```

**核心差异：时钟是否显式存在**：
```
DP：算一次就完，纯计算，没有时间维度
状态机：每个时钟沿无限循环转移，多了"时钟锁存"的时间维度
→ 状态机 = 带时钟的 DP（时钟化的动态规划）
→ 高级语言写 DP 时"自动忽略了时钟"，硬件里时钟必须显式存在
```

**一句话**：软件写状态/递推时编译器/运行时帮你把"什么时候更新"（时钟）藏起来了；硬件（FPGA）里时钟是物理存在，必须显式写出（`@(posedge clk)`）。**这就是软件 vs 硬件的终极分界——不是"有没有状态"，是"时钟是否显式"**。你在软件里写 DP 的直觉（状态+转移+取结果）和写状态机是同一条，只是硬件逼你把"时钟"这层明明白白摆出来。

### 跨时钟域 CDC
```
- 慢→快：打两拍同步（两级寄存器）
- 快→慢：握手 / FIFO
- 单 bit 信号：双触发器同步器
- 多 bit 信号：异步 FIFO / 格雷码
```

### 亚稳态 metastability
```
- 建立/保持时间违规 → 触发器输出不确定
- 不能消除，只能降低概率（打两拍）
- 打两拍后仍 X → 检查时钟关系/约束
```

### 异步 FIFO
```
- 读写不同时钟域
- 指针用格雷码 + 打拍同步
- 满/空判断（领先/滞后位）
```

### 布线局部性（硬件版局部性原理）

FPGA 也有"局部性"，比 CPU 更物理，方向相反：

```
软件局部性（优化，影响快慢）      FPGA 对应
──────────────                ──────────
空间局部性（附近数据一起用）  →  布线局部性（相关逻辑放近，走线短）
时间局部性（频繁一起用）      →  触发器/逻辑簇（同 always 的 reg 放同 CLB）
缓存预取（猜下一步碰哪）      →  nextpnr 布局布线优化（自动把相关逻辑放近）
```

**关键区别**：软件里局部性是性能优化（缓存没命中 → 慢一点）；FPGA 里布线局部性是**生死**（走线太长 → 时序不收敛 → 设计跑不到目标频率甚至综合失败）。

**你的影响手段**：
- 模块划分清晰 → 相关逻辑天然近
- 状态机编码、流水线深度 → 决定综合工具能不能布好
- nextpnr 干的就是"把相关逻辑物理放近"——硬件版缓存预取

### 流水线：把一个大 τ 拆成多个小 τ

**本质**：组合逻辑链太长 → 总延迟 τ_总 大 → 时钟周期必须 > τ_总 → 频率低。流水线 = 在组合逻辑中间插寄存器，切成多段，让各段**并行处理不同数据**。

```
无流水线：τ_总 = τ1+τ2（整条链延迟累加）→ 时钟周期 > τ1+τ2
流水线：插寄存器切两段 → 时钟周期 > max(τ1, τ2)（各段独立计时）
→ τ_总（累加）变成 max(各段τ) → 频率和吞吐提升
```

**结构对比**：
```
无流水线：寄存器 ──→ [组合逻辑 τ1+τ2] ──→ 寄存器
流水线：寄存器 ──→ [组合1 τ1] ──→ 寄存器 ──→ [组合2 τ2] ──→ 寄存器
```

**关键点**：
- **门延迟（每个 τ）本身没变小**，变小的是"时钟周期"（从累加变 max）
- 靠"切段 + 并行"提速：多段同时处理不同数据（像流水线工厂，工位没变快，但多个工位同时干活）
- **代价**：单条数据延迟变多拍（要过 N 级寄存器）——**流水线用"延迟换吞吐"**
- 这和"打两拍/触发器串联"同一条原理（组合间插寄存器），只是目的不同：同步（CDC）/ 提速（流水线）

**一句话**：流水线 = 把一个大 τ（整条组合链延迟）拆成多个小 τ，插寄存器切段并行，时钟周期从"τ_总 累加"变成"max(各段τ)"，频率和吞吐提升 N 倍。门延迟不变，变的是时钟周期；用延迟换吞吐。
