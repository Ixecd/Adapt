# K8s随笔

## 什么是K8s?
- 就是帮我们管理容器应用(云平台多主机),目标让部署容器化应用更简单,更高效,更可靠.

## 为什么需要K8s?
**传统部署**
- 源程序打包成镜像,上传到Tomcat服务器,启动Tomcat服务器,然后访问应用.

**问题**
- 所有的操作都是人工完成的,很麻烦,效率低,部署效率低(如果服务器配置比较高的化,只部署一个服务就会浪费.如果部署多个服务,这多个服务会共享内存非常危险),容易出错,不方便管理.
- 用户通过网络访问服务器,访问密集的服务会占据更多的网络带宽,影响其他用户的使用.

**虚拟化部署**
- 源程序打包成镜像,上传到云平台(一个服务器上多个虚拟机,每个虚拟机上都有一个服务,类似容器,环境隔离),效率不高,开销大.

**容器化部署**
- **容器**:Linux内核中使用创建一个新进程+名字空间+组隔离机制实现

**Q:进程之间本身不就是隔离的吗??**
- A:进程只能保证基本隔离,并不能满足容器化所需要的更复杂的隔离需求,**容器**提供的隔离不仅仅是进程之间的隔离,而是通过更需力度的资源和环境隔离来提供多重安全和独立性
- 进程隔离是基于进程的逻辑分离,并不会改变进程在操作系统内的其他环境,不同的进程仍然共享宿主机的**内核**和**资源**
- 容器虽然也是进程,但是通过**namespace**和**cgroup**实现更深度的隔离.容器不仅仅隔离了进程,还隔离了许多其他系统资源,比如**文件系统/网络栈/进程ID/用户ID/进程见通信/资源限制等**,容器内的进程不会看到宿主机或其他容器的资源

## K8s核心概念

1. 无状态服务和有状态服务
- 状态即数据,有状态表示存储了数据,无状态表示未存储数据
- Nginx -> 无状态服务(不会对本地环境产生任何依赖)
- Redis -> 有状态服务(对本地环境具有一定依赖性,依赖文件系统/硬盘),多了数据迁移和同步的操作

2. 对象规约和状态
- 资源通过配置文件描述(json/yaml 大头在yaml)
- 对象就是基于资源具体化而来
- 规约(spec),描述的是对象的期望状态
- 状态(status),描述对象的实际状态,由K8s自己维护,通过一系列控制器对对应对象进行管理,让对象尽可能让实际状态向期望状态靠拢

3. 资源的分类
- 元空间:对于资源元数据描述,每一个资源都可以使用元空间的数据
- 集群:作用于集群之上,集群下的所有资源都可以共享使用,集群下可以有多个命名空间
- 命名空间:命名空间之间是隔离的,互相访问不到对方的资源,只能在该命名空间之内使用

4. 元数据型和集群型资源
- **元数据型**
    - Horizontal Pod Autoscaler(HPA), Pod自动扩容,根据CPU使用率或自定义指标自动对Pod进行扩/缩容
    - PodTemplate,Pod的定义
    - LimitRange, 对集群内的资源进行一个限制,限制用多少资源
- **集群类型资源**
    - Namespace 命名空间
    - Node,K8s不创建只管理
    - ClusterRole 集群级别权限管理
    - ClusterRoleBinding 角色与资源绑定,只能与集群类型资源绑定,绑定到集群
- **命名空间级**
    - Pod, Pod可以包含多个容器,如果没有Pod,容器之间的网络通信就会有很大阻碍,并且容器对存储卷有同步问题,通过Pod可以当两个容器有强依赖关系的时候可以共享网络,共享文件系统
    - 每一个Pod被创建出来都会有一个**pause**容器,实现共享功能
    - 一般情况下,一个Pod里只会有一个应用容器,除非有强耦合关系才会将多个应用编排在一起
    - 副本(replicas),创建Pod通过PodTemplate,可以基于一个Pod对象创建副本,除了名字/uid不同,其他都相同
    - 控制器,副本在控制器里面,每个控制器通常包含一个副本属性

5. 控制器RC/RS/Development
    - 控制器(内存上的一个对象,实际还是一个Pod,只是定义了很多专门用来描述这个对象的参数)
    - 适用于无状态服务的控制器
        - ReplicationController (RC,已经寄了) 动态更新Pod的副本数量
        - ReplicaSet (RS,实际生产环境中也不会用)  功能和RC一样,但是可以通过selector选择对哪些Pod生效,可以给Pod加标签
        - **Development** 对RS再做一次封装,提供更丰富部署相关的特性,更轻松更方便
            - 自动创建RS和Pod
            - 自动滚动升级/回滚
            - 平滑的扩容/缩容 通过RS,RS来扩缩容

6. 有状态服务控制器
    - StatefulSet:针对于有状态服务进行部署的状态器
    - 滚动升级 会先关闭所有的Pod,重新构建
    - Headless Service 有状态服务的DNS管理
    - volumeClaimTemplate pvc 持久化存储

7. Daemonset守护进程与任务
    - 为每一个匹配的Node都部署一个守护进程

8. 任务和定时任务
    - 任务执行完后,Pod销毁,不再创建新的容器
    - CronJob再Job基础上添加了定时功能

9. Service 和 Ingress 服务发现控制器
    - 流量分为东西流量和南北流量,东西流量通过Service进行流量调度,南北流量通过Ingress进行流量调度
    - 自上而下的流量被称为纵向流量(南北流量)
    - 微服务与微服务之间有横向的调用关系,这种流量称为横向流量(东西流量)
    - Service : K8s集群内,节点与节点之间的通信,Pod和Pod之间的通信,包括负载均衡,基于网络层
    - Ingress : 外部访问集群内部服务的入口,提供负载均衡(nginx七层负载),TLS/SSL,HTTP/HTTPS转发等功能
    - 跨机器的Pod之间的网络是不共享的,需要通过Service进行流量调度,Service通过暴露接口可以让其他Node中的Pod访问该Node中的Pod
    - Ingress又是Service的又一层封装,用户通过Ingress(统一的入口,暴漏到外网,反向代理,七层负载) 访问 Service

10. 存储/配置/角色
    - 存储:
        - Volume : 存储卷,虚拟数据卷,共享Pod中容器使用的数据
        - CSI : 标准接口,提供容器存储接口存储插件,可以对存储进行管理

    - 特殊类型配置:
        - ConfigMap : KV的配置,保存配置信息,加载到Pod中,让Pod中的容器所需要的数据暴漏出来
        - Secret : 多加了一层保密性,保存敏感信息,比如密码,证书等
        - DownwardAPI : Pod的信息共享到容器内
    
    - 角色:
        - Role : 角色,权限管理,命名空间级别可以对K8s资源进行细粒度控制
        - RoleBinding : 角色绑定,直接可以作用于Role 和 ClusterRole,可以将角色绑定到用户或用户组,让用户拥有相应的权限,绑定到命名空间
